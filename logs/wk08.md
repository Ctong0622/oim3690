## Session 14 – JavaScript Arrays and Loops

This week I learned how JavaScript arrays can store multiple related values in one variable. I practiced accessing items in an array and learned that array indexes start at 0. I also learned that `.length` can tell me how many items are in an array.

I learned how loops can be used to repeat the same action for every item in an array. The main loop I practiced was `for...of`. Instead of writing the same code separately for every song, I can use a loop to go through the entire array one item at a time.

I also practiced combining loops with conditionals. In the playlist exercise, I used an `if` statement to check whether a song title contained the word "Remix". This helped me understand how a loop can process every item while still treating some items differently based on a condition.

Session 15 – Project Presentations and Feedback

In Session 15, I spent time looking at other students' projects and presentations. I found it useful because even when people were building similar types of projects, their final websites could look and feel very different.

One thing I noticed was the difference between Sam's and Alice's projects. Their projects had some similarities, but I liked how Sam used different font sizes with CSS. The different font sizes made some information stand out more and made the page easier to look at. Alice's project had a different style even though some parts of the projects were similar.

This made me realize that CSS is not only about changing colors or making a website look nice. Font size, spacing, layout, and visual hierarchy can make a big difference in how easy a website is to understand. Two projects can have similar functions but still give users very different experiences because of their design choices.

Another thing I noticed during the presentations was how important it is to test unusual inputs. In one project, I noticed that the time input could accept a value like 1e20. I do not remember exactly whose project it was, but that value is obviously an unrealistic amount of time.

The website could technically accept the number, so the code might look like it is working correctly, but the result does not make sense for a real user. This made me think about setting reasonable limits for inputs. For something like time, there should probably be a maximum value instead of allowing any number.

It also showed me that testing a project should include more than just normal inputs. If I only test the values I expect users to enter, I might miss problems like this. Users can type unexpected or unrealistic values, so I should think about minimum values, maximum values, empty inputs, and other unusual cases.
