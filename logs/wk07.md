## Session 13 – JavaScript Essentials and Conditional Logic

This week was mostly about finishing up the JavaScript essentials slides, and the big theme was conditionals — `if`, `else if`, `else`, and how JavaScript actually decides which one to run. We also went back over some data type stuff that I needed to be solid on before any of the conditional logic would make sense.

1. **Data types (strings, numbers, booleans).** I practiced telling the difference between the three basic types I'm using the most right now: strings (text, like `"hello"`), numbers (like `20`), and booleans (`true` or `false`). Using `typeof` on a value in the console tells me which one it is — `typeof "20"` gives `"string"` and `typeof 20` gives `"number"`, even though they look almost the same to me as a human reading them.

2. **Why `"20" + 10` is `"2010"` and not `30`.** This one actually tripped me up. If one side of a `+` is a string, JavaScript doesn't do math — it glues the two values together as text instead. So `"20" + 10` becomes the string `"2010"`, not the number `30`. This matters a lot for my discount project because the cart total comes out of an `<input>` box as a string, even when I type numbers into it.

3. **`Number()` and why I need it.** Because anything typed into an HTML input is text (a string), I have to convert it with `Number()` before I can use `>=` or do math with it correctly. In `discount.html` I used `const total = Number(totalInput.value);` so that `total` is an actual number and not a string that just looks like one. Without that conversion, `total >= 100` could behave in ways I wouldn't expect, and `total - discount` could turn into string concatenation instead of subtraction.

4. **`const` with arrays and objects — mutation vs. reassignment.** We also looked at how `const` works differently for arrays/objects than it does for plain values. `const` stops me from reassigning the variable itself (I can't do `myArray = []` again), but it does **not** stop me from changing what's inside the array or object, like pushing a new item in. That's the difference between mutating something (changing its contents) and reassigning it (pointing the variable at something new). I'm still getting used to this one, but it makes more sense now than it did before.

5. **Functions and `return`.** I practiced the difference between a function that just does `console.log(...)` and one that uses `return`. A function without `return` hands back `undefined` to whatever called it, even if it printed something useful to the console. A function with `return` actually gives a value back that I can store in a variable and reuse, like `const discount = getDiscount(total, isMember);` in my discount project.

6. **`if`, `else if`, `else`, and comparisons like `>=`.** This is the core of what I practiced this week. An `if / else if / else` chain checks its conditions from top to bottom and runs the **first** one that's true — it doesn't keep checking after that. I used `>=` a lot (for example `total >= 100`) to check "100 or more," not just "more than 100."

7. **`&&` vs `||`.** `&&` means both sides have to be true for the whole thing to be true. `||` means only one side needs to be true. In my discount function, `total >= 100 && isMember` only counts as true if the total is big enough **and** the person is a member. `total >= 100 || isMember` is true if either one of those is true, even just one.

8. **Why the order of the branches matters.** This was the main "aha" of the week. Because an `if / else if` chain stops at the first true condition, putting the branches in the wrong order can quietly give the wrong answer even though the conditions themselves are written correctly. I actually tested this myself on my own discount function (see the next section), and it's the thing that made this concept really click for me instead of just being something I was told.

## Member Discount Exercise

For this exercise I built `discount.html`, a small page with a cart total input, a membership checkbox, and a "Check Discount" button. When I click the button, it reads the total and whether I'm a member, runs them through a `getDiscount(total, isMember)` function, and shows me the discount amount and the final price after the discount is subtracted.

The function I wrote looks like this:

```js
function getDiscount(total, isMember) {
    if (total >= 100 && isMember) {
        return 20;
    } else if (total >= 100 || isMember) {
        return 10;
    } else {
        return 0;
    }
}
```

The rules, based on the slides, were: $20 off if the total is $100 or more **and** the person is a member, $10 off if **either one** of those is true on its own, and $0 off if neither is true.

Before I even wrote the function, I tried to predict how it should behave in my head: a big order from a member should get the best discount, a big order from a non-member or a small order from a member should get something in between, and a small order from a non-member should get nothing. Once I wrote it, I could see that this is exactly what the `&&` and `||` were doing — `&&` in the first branch makes sure *both* conditions are true before giving the full $20, and `||` in the second branch lets *either* condition on its own be enough for the smaller $10 discount.

To check my own work, I tested $150 in the cart total box twice: once with the membership checkbox checked and once with it unchecked. With the box checked, the page showed a $20 discount, which matched my prediction since $150 is over $100 **and** I marked myself as a member. With the box unchecked, the page showed a $10 discount instead, since only the "$100 or more" condition was true and the membership condition wasn't. Seeing the discount actually change just from checking or unchecking that one box was a good small confirmation that `isMember` was really being read correctly by the function.

**The branch-swapping experiment.** To really test whether I understood the "order matters" idea, I temporarily swapped the first two branches so the function checked `total >= 100 || isMember` first and `total >= 100 && isMember` second. Before testing it, I predicted that a $150 cart total with the membership box checked would now come out as a **$10 discount instead of $20**, because the `||` condition would already be true and JavaScript would stop right there without ever checking the `&&` condition underneath it.

I tested this in the browser with $150 and the member box checked, and I actually got **$10**, exactly like I predicted. This confirmed why the order of the branches matters: JavaScript stops at the very first condition that evaluates to `true` and never looks at the rest of the chain, even if a later condition would have also been true (or "more true," like the `&&` case). After confirming this, I put the branches back in the correct order (`&&` check first, `||` check second) so the function matches the actual rules again.

**Adding the final price ("Make It Yours").** For the extra part of the exercise, I added a final price calculation so the page doesn't just show the discount amount but also what I'd actually owe after the discount:

```js
checkButton.addEventListener('click', () => {
    const total = Number(totalInput.value);
    const isMember = memberCheckbox.checked;
    const discount = getDiscount(total, isMember);
    const finalPrice = total - discount;
    result.textContent = `Your discount is $${discount}. Final price: $${finalPrice}`;
});
```

For my final test, I entered $150 with the membership box checked, and the page showed a **$20 discount** with a **$130 final price**, which matches the math ($150 − $20 = $130) and the correct rule (total ≥ 100 and member = $20 off).

## What I Learned

Looking back at this week, I feel like I'm slowly shifting from "ask the AI to write it and see if it works" to actually reading the JavaScript myself and thinking about what each line is doing before I run anything. The discount function is a good example — instead of just trusting that `&&` and `||` were in the right spots, I made myself predict what the swapped version would do first, and then checked the browser to see if I was right. Being able to say "I think this will show $10" before clicking the button, and then actually getting $10, felt a lot more solid than just staring at code and hoping it's correct.

Understanding data types better also helped a lot this week. The `"20" + 10` example made it click why `Number()` isn't just a formality — if I skip it, my "math" could silently turn into string-gluing instead, and I might not even notice until something looks weird. Same with `const` and mutation versus reassignment; I used to think `const` meant "this can never change in any way," and now I get that it's really about not being able to point the variable at something new, not about freezing everything inside it.

The order-of-conditions idea tied everything together for me. It's not enough to know that `if / else if / else` exists — I have to actually trace through which branch will run first for a given input, especially once there's more than one condition that could technically be true at the same time. Before this week I probably would have just asked my agent to "write me a discount function" and trusted whatever came back as long as it ran without errors. This week I actually sat with the logic myself, worked out what each branch should do, and only then checked whether the code matched what I expected.

I think the biggest shift for me this week is that I'm starting to test my own predictions instead of only testing whether code runs. Running code and seeing no errors used to feel like "it works." Now I know that's not the same as it working *correctly* — the swapped-branch version of `getDiscount` ran perfectly fine with zero errors, and it still gave the wrong discount. The only way I caught that was by predicting an answer first and then checking it against the real browser output, which is a habit I want to keep using as the code I write gets more complicated. I'm still a beginner at this, and I still lean on my agent a lot to generate the first draft of something, but I'm getting more comfortable reading what it gives me line by line, asking myself what each `if`, `return`, or comparison is actually doing, and figuring out *why* something works instead of just confirming that it does.
